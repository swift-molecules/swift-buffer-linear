# swift-buffer-linear

Use this package when you need elements, copyable or not, packed contiguously from slot zero in storage you choose through `S`, with appends at the back. Start from `Buffer.Linear` when the buffer should grow, and from `Buffer.Linear.Bounded` when capacity is a hard ceiling that must never reallocate. Removing from the front is linear time here, because every remaining element shifts down. For a queue, sparse slots or linked nodes, use a sibling package instead: swift-buffer-ring, swift-buffer-slab, swift-buffer-slots or swift-buffer-linked.

## Laws

- The initialized elements are always the slots from zero up to `count`. `Buffer.Linear.Header.initialization` is either `.empty` or `.one` covering exactly that range, never anything else. Setting `initialization` on `Buffer.Linear` to a shape that is not a prefix traps.
- Through the generic `Store.Protocol` seam, `initialize(at:to:)` accepts only the slot equal to `count`, and `move(at:)` accepts only the last initialized slot. Any other slot traps instead of letting `count` drift. `swapAt` accepts any two initialized slots, and swapping a slot with itself changes nothing.
- `remove(at:)` and front removal keep the order of the remaining elements by shifting them down. `remove(at:)` traps when the index is not below `count`.
- When a full `Buffer.Linear` gets an `append`, its capacity doubles (from zero it becomes one), and every element moves into new storage. `reserveCapacity` grows the buffer only when you ask for more than it already has, and never shrinks it. `reallocate(capacity:)` can grow or shrink, and traps when asked for less than `count`. The allocator may round capacity up, so `Buffer.Linear` capacity is at least what you asked for, not exactly that.
- `Buffer.Linear.Bounded` capacity is exactly the capacity you asked for, whatever the allocator provides. When an `append` finds the buffer full, it returns the element it was given and leaves the buffer unchanged. It returns `nil` when the element was stored. Building one from an array or a builder block throws before storing anything when there are more elements than capacity.
- `clone()` on `Buffer.Linear` sizes the copy's capacity to `count`, not to the source's capacity. `clone(capacity:)` traps when the capacity is below `count`. `clone()` on `Buffer.Linear.Bounded` keeps the exact capacity. Either way the copy shares no storage with the source.
- `split(maximum:)` consumes the buffer. The prefix gets the first `maximum` elements, or all of them when there are fewer, and the remainder gets the rest, each keeping its order, and each part gets its own new storage sized to its count.
- `removeAll()` and `drain` keep capacity, and `drain` hands over elements from front to back. `removeAll(keepingCapacity: false)` replaces the storage with an empty, zero-capacity allocation. `truncate(to:)` does nothing when the new count is not below `count`.
- With the `OutputSpan` entry points, `count` becomes however many elements the span holds when the closure returns or throws. If `edit` or `append(addingCapacity:initializingWith:)` throws, the elements appended before the throw stay in the buffer. `edit` covers the whole capacity, and the span in `append(addingCapacity:initializingWith:)` has exactly `addingCapacity` free slots, after the buffer has grown to make room for them.
- `Buffer.Linear.Builder` stores elements in source order. A `nil` optional, a skipped `if` and an empty block contribute nothing.
